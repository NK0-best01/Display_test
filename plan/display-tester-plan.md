# แผนพัฒนาแอปทดสอบจอ (Display Tester) ด้วย Tauri

เอกสารนี้เขียนให้ AI ผู้พัฒนาอ่านและทำงานเป็นส่วน ๆ (Part) ตามลำดับ

## 0. กติกาการทำงานของ AI (อ่านก่อนเริ่ม)

1. ทำงานทีละ Part ตามลำดับ จบแต่ละ Part ให้สรุปสิ่งที่ทำ วิธีรัน และหยุดรอผู้ใช้ยืนยันก่อนเริ่ม Part ถัดไป
2. หากข้อกำหนดใดไม่ชัดเจนหรือขัดกัน ให้ถามผู้ใช้ก่อนเขียนโค้ด ห้ามเดาในเรื่องที่กระทบสถาปัตยกรรม
3. ห้ามเพิ่มฟีเจอร์นอกขอบเขต (เช่น บันทึกผล ส่งออกรายงาน วัด response time ของพาเนลด้วยกล้อง)
4. โค้ดต้องรันได้จริงบน Linux และ Windows ห้ามใช้ API เฉพาะ OS ถ้าไม่จำเป็น
5. ทุก Part ต้องผ่านเกณฑ์ตรวจรับ (Acceptance Criteria) ของ Part นั้นก่อนถือว่าเสร็จ

## 1. ข้อกำหนดโดยรวม

| หัวข้อ | รายละเอียด |
|---|---|
| Framework | Tauri v2 (Rust backend + WebView frontend) |
| ประเภทแอป | Desktop app รันบน Linux และ Windows |
| ขนาดจอ | Responsive ตามขนาดจอ desktop ทุกขนาด รวมถึง 1024 x 768 (4:3) ซึ่งเป็นจอที่ใช้ทดสอบจริง (ไม่ใช่ขนาดหน้าต่างแอป) |
| ผลการทดสอบ | แสดงบนหน้าจอเท่านั้น ไม่บันทึกไฟล์ ไม่ส่งออก |
| ภาษา UI | ไทยอย่างเดียว (ผู้ใช้ยืนยันแล้ว) |

### รายการทดสอบทั้งหมด

1. คุณภาพของภาพ (Image Quality)
2. ทดสอบ Touch (Multi-touch และการวาด)
3. ทดสอบสี (Color)
4. Dead Pixel / Stuck Pixel
5. แสงรั่วและความสม่ำเสมอของแสง (Light Bleed / Mura)
6. เช็คทิศทาง Touch (แกน X/Y กลับด้านหรือสลับแกน)
7. Touch-to-Paint Latency (ความหน่วงของ touch ในแอป)

## 2. สมมติฐานและข้อจำกัดที่ต้องรู้

- **ขนาด 1024x768:** คือความละเอียดของจอที่ถูกทดสอบ (อัตราส่วน 4:3) แอปต้องรันแบบเต็มจอ (Fullscreen) บนจอนี้ ออกแบบเมนูและ HUD ให้ responsive ใช้ได้กับทุกขนาดจอ desktop รวมถึง 1024x768 ส่วนหน้าทดสอบใช้ความละเอียดจริงของจอที่รันอยู่เสมอ เพราะการหา dead pixel และ mura ต้องครอบคลุมทุกพิกเซล
- **Response Time:** วัดเฉพาะ touch-to-paint latency ด้วยซอฟต์แวร์ (เวลาจาก event เข้า จนถึงเฟรมที่วาดผลเสร็จ) ไม่รวมความหน่วงของพาเนลจอ ต้องแจ้งข้อจำกัดนี้ให้ผู้ใช้เห็นในหน้าผลลัพธ์
- **Touch ใน WebView:** ใช้ Pointer Events เป็นหลัก มี fallback เป็น Touch Events หาก WebKitGTK บน Linux (X11) ทำงานผิดปกติ
- **การแสดงสี:** ผลที่เห็นขึ้นกับ color profile ของระบบและ WebView ให้ใช้สีดิบ (sRGB) ไม่ใส่ filter หรือ effect ใด ๆ ทับ
- **Display scaling:** Windows และ Linux อาจตั้ง scale 125%, 150% ต้องคำนึง `devicePixelRatio` เพื่อให้ pattern แบบ 1 พิกเซลคม (pixel-perfect)

## 3. สถาปัตยกรรมที่แนะนำ

- **Frontend:** Vite + TypeScript (Vanilla TS ไม่ใช้ UI framework) + Tailwind CSS v3.4 สำหรับเมนู HUD และหน้าสรุป ส่วนภาพทดสอบวาดด้วย `<canvas>` 2D หรือ WebGL
- **Backend (Rust):** เบาที่สุดเท่าที่ทำได้ ใช้แค่ window API ของ Tauri (fullscreen, ข้อมูล monitor) ไม่ต้องมี command ซับซ้อน
- **โครงสร้างโฟลเดอร์ (ข้อเสนอ):**
  - `src/main.ts` จุดเริ่มต้นและ router
  - `src/core/` ได้แก่ ตัวจัดการ fullscreen, input, overlay HUD, ข้อมูลจอ
  - `src/tests/` โมดูลทดสอบแยกไฟล์ต่อหนึ่งหัวข้อ
  - `src/ui/` เมนูหลักและหน้าสรุป
- **อินเทอร์เฟซโมดูลทดสอบ:** ทุกโมดูลมี `start(canvas, ctx)`, `stop()`, `onKey(e)` และ `onPointer(e)` เพื่อให้เพิ่มโมดูลใหม่ได้ง่าย

## 4. แผนงานแยกเป็น Part

### Part 1: สร้างโปรเจกต์และโครงแอป (Scaffold)

**งาน**

- สร้างโปรเจกต์ Tauri v2 พร้อม TypeScript และ Vite
- ตั้งค่า `tauri.conf.json`: เปิดแอปแบบเต็มจอ (fullscreen) เป็นค่าเริ่มต้น ตามขนาดจอจริงของเครื่อง ปิดขอบหน้าต่าง (decorations: false) ไม่ล็อกขนาดหน้าต่าง และมีโหมด dev เปิดเป็นหน้าต่างที่ปรับขนาดได้ สำหรับพัฒนาและทดสอบ responsive บนจอที่ใหญ่กว่า
- ติดตั้ง Tailwind CSS v3.4 (PostCSS + Vite) ใช้กับเมนู HUD และหน้าสรุปผลเท่านั้น หน้าทดสอบที่วาดบน canvas ห้ามมี filter, backdrop-blur, shadow, opacity หรือ transition ทับบริเวณทดสอบ ปุ่มสำหรับทัชกว้างและสูงอย่างน้อย 64 พิกเซล ใช้ breakpoint ของ Tailwind ให้ responsive ตามขนาดจอ และต้องใช้งานได้ดีบนจอ 1024x768 ด้วย
- ตั้งค่า capabilities ให้เรียก `setFullscreen` และอ่านข้อมูล monitor ได้
- ปิด context menu, การเลือกข้อความ, การซูมด้วย pinch และ scroll bounce (`touch-action: none` ในหน้าทดสอบ)
- เพิ่มสคริปต์ `dev` และ `build` และเขียน README ขั้นตอนติดตั้ง prerequisites ของ Linux (webkit2gtk-4.1 ตามเอกสาร Tauri v2) และ Windows (WebView2, MSVC build tools)

**เกณฑ์ตรวจรับ**

- `npm run tauri dev` เปิดแอปเต็มจอพอดีขนาดจอจริง (ทดสอบที่ 1024x768 และขนาดอื่น) บนทั้ง Linux (X11) และ Windows โดยไม่มีขอบหรือแถบบัง
- กด F11 สลับ Fullscreen ได้ และกด Esc ออกจาก Fullscreen ได้

### Part 2: โครงหลักของแอป (App Shell)

**งาน**

- หน้าเมนูหลัก (responsive ตามขนาดจอ) แสดงปุ่มใหญ่สำหรับทดสอบ 7 หัวข้อ ใช้งานได้ทั้งเมาส์และทัช (ปุ่มใหญ่ กดง่าย)
- ระบบ router ระหว่างเมนูกับหน้าทดสอบ ปุ่ม Esc หรือการกดค้างมุมจอย้อนกลับเมนู (สำคัญมากสำหรับจอทัชที่ไม่มีคีย์บอร์ด)
- ทุกหน้าทดสอบแสดงเต็มจอ ขนาด canvas เท่าความละเอียดจริงของจอ (เช่น 1024x768) ไม่มีขอบหรือแถบเมนูบัง
- HUD เล็ก ๆ มุมจอ แสดงชื่อทดสอบและคำสั่ง ซ่อน/แสดงด้วยปุ่ม H หรือแตะสามนิ้ว
- หน้า Info แสดงความละเอียดจริง, `devicePixelRatio`, ชื่อ monitor, `navigator.maxTouchPoints`, OS
- กำหนดอินเทอร์เฟซโมดูลทดสอบตามหัวข้อ 3

**เกณฑ์ตรวจรับ**

- เข้าและออกหน้าทดสอบจำลอง (placeholder) ได้ด้วยเมาส์, คีย์บอร์ด และทัช
- ไม่มี memory leak เมื่อสลับหน้าไปมา 50 ครั้ง (ล้าง listener และ requestAnimationFrame ทุกครั้งใน `stop()`)

### Part 3: ทดสอบคุณภาพของภาพ (Image Quality)

**ภาพทดสอบ (สลับด้วยลูกศรซ้าย/ขวา หรือปัดนิ้ว)**

1. Grayscale ramp ต่อเนื่อง และแบบขั้นบันได 16 และ 32 ระดับ (ดู banding และการแยกระดับสีเทา)
2. Near-black และ near-white (ช่วง 0-15 และ 240-255) สำหรับตรวจการสูญเสียรายละเอียดในส่วนมืดและสว่าง
3. Gamma pattern (เส้นสลับขาวดำเทียบกับเทา 50%)
4. Sharpness: เส้น 1 พิกเซลแนวนอน/แนวตั้ง, ตารางหมากรุก 1 พิกเซล, ข้อความขนาดเล็ก
5. Geometry: วงกลมและตารางเส้นเต็มจอ ตรวจความเพี้ยนของอัตราส่วนและการ scale ผิดปกติ
6. Overscan/edge: กรอบเส้นบางที่ขอบสุดของจอ ตรวจว่าขอบไม่ถูกตัด

**หมายเหตุ:** ต้องวาดแบบ pixel-perfect โดยคูณขนาด canvas ด้วย `devicePixelRatio` และใช้ `image-rendering: pixelated`

**เกณฑ์ตรวจรับ**

- เส้น 1 พิกเซลคมชัด ไม่เบลอ แม้ตั้ง scale 125-150%
- เปลี่ยนภาพทดสอบได้ทั้งคีย์บอร์ดและทัช

### Part 4: ทดสอบสี (Color)

**ภาพทดสอบ**

1. สีเต็มจอ: แดง เขียว น้ำเงิน ขาว ดำ ฟ้าอมเขียว (cyan) ม่วงแดง (magenta) เหลือง
2. Color bars แบบ SMPTE หรือ 8 แท่งมาตรฐาน
3. Gradient แยกช่องสี R, G, B และสีผสม (ตรวจ banding)
4. ช่องสีเทียบ (patch) สำหรับสีผิว สีท้องฟ้า สีหญ้า เพื่อดูด้วยสายตา
5. White/Gray tint: ขาวและเทา 25%, 50%, 75% เพื่อตรวจสีเพี้ยน (เช่น เหลืองหรือเขียวเจือ)

**เกณฑ์ตรวจรับ**

- ค่าสีที่วาดตรงตามนิยาม (ตรวจด้วยการอ่าน pixel จาก canvas ในโหมด debug)
- ไม่มี filter, shadow หรือ transition ใด ๆ ทับ

### Part 5: ทดสอบ Dead Pixel / Stuck Pixel

**งาน**

- วนสีเต็มจอ: ดำ ขาว แดง เขียว น้ำเงิน (กดเปลี่ยนด้วยคลิก, ลูกศร หรือแตะ)
- จุดดำบนพื้นสีสว่าง = Dead pixel, จุดสว่าง/สีบนพื้นดำ = Stuck/Hot pixel
- Magnifier: แว่นขยายตามนิ้วหรือเมาส์ (ขยาย 4-8 เท่าแบบ nearest-neighbor) ช่วยตรวจจุดเล็ก
- ตัวนับ: ผู้ใช้กดมาร์กตำแหน่งที่พบจุดเสีย และแสดงจำนวนกับพิกัด (เก็บเฉพาะในหน่วยความจำและแสดงบนหน้าจอ ไม่บันทึกลงไฟล์)
- ตัวเลือกซ่อนเคอร์เซอร์และ HUD เพื่อไม่บังจอ

**เกณฑ์ตรวจรับ**

- เติมสีเต็มทุกพิกเซลโดยไม่มีขอบเว้น (รวมแถบขอบจอ)
- Magnifier ทำงานได้ลื่นบนทัช

### Part 6: ทดสอบแสงรั่วและความสม่ำเสมอของแสง (Light Bleed / Mura)

**ภาพทดสอบ**

1. จอดำสนิท (RGB 0,0,0) ตรวจ backlight bleed ที่ขอบและมุม
2. เทาเข้มหลายระดับ (เช่น 5%, 10%, 15%, 20%) ที่เผยจุดด่างและ clouding
3. เทากลาง 50% สำหรับตรวจ mura และเงาเป็นปื้น
4. ขาวเต็มจอ ตรวจความสว่างไม่เท่ากันและ vignette
5. โหมดตาราง 3x3 / 5x5 แสดงบล็อกเทาเท่ากัน เพื่อเทียบความสว่างระหว่างโซน

**ฟีเจอร์ประกอบ**

- ปรับระดับเทาด้วยปุ่ม +/- หรือสไลเดอร์แตะได้
- ซ่อน UI ทั้งหมดอัตโนมัติ และมีคำแนะนำว่า ให้ทดสอบในห้องมืดและมองจากหน้าตรง

**เกณฑ์ตรวจรับ**

- ระดับเทาเปลี่ยนละเอียดทีละ 1/255 ได้
- ไม่มีองค์ประกอบ UI ค้างบนจอระหว่างทดสอบ

### Part 7: ทดสอบ Touch (Multi-touch)

**งาน**

- วาดจุดและเส้นตามนิ้วแต่ละนิ้ว (สีต่างกันตาม `pointerId`) แสดงจำนวนจุดสัมผัสพร้อมกัน สูงสุดที่ตรวจเจอ และค่า `maxTouchPoints`
- โหมด Draw: วาดเส้นต่อเนื่อง ดูความต่อเนื่องและการสะดุดของเส้น (ใช้ `getCoalescedEvents`)
- โหมด Grid: แบ่งจอเป็นช่อง (เช่น 16x12) แตะ/ลากให้เปลี่ยนสีช่องทีละช่อง เพื่อตรวจว่าทัชครอบคลุมทั้งจอ รวมถึงขอบและมุม มีปุ่มรีเซ็ต
- แสดงข้อมูลสดข้างจุด: พิกัด, pressure, ขนาดสัมผัส (ถ้ามี) ในพื้นที่ HUD
- ตั้ง `touch-action: none` และป้องกัน gesture ของระบบแทรกแซง

**เกณฑ์ตรวจรับ**

- รองรับอย่างน้อย 10 จุดพร้อมกันตามความสามารถของฮาร์ดแวร์
- ผู้ใช้เห็นช่อง Grid ที่ยังไม่ถูกแตะ จึงรู้ว่ามีโซนไหนทัชไม่ติด

### Part 8: เช็คทิศทาง Touch (Axis / Orientation)

เป้าหมาย: ตรวจว่าตำแหน่งที่แตะตรงกับตำแหน่งที่แสดงบนจอ หรือกลับด้าน/สลับแกน

**ขั้นตอนทดสอบ**

1. แสดงเป้า (วงกลมพร้อมเลขลำดับ) ที่ 4 มุม ตามลำดับ บนซ้าย → บนขวา → ล่างขวา → ล่างซ้าย (ตำแหน่ง 10% จากขอบ)
2. ผู้ใช้แตะที่เป้าแต่ละจุด เก็บพิกัดที่แตะ (normalize เป็น 0-1 ตามขนาดจอ)
3. ประมวลผลหาการแปลงที่ตรงที่สุดจาก 8 รูปแบบ: ปกติ, กลับแกน X, กลับแกน Y, หมุน 180°, สลับ X↔Y, สลับ X↔Y พร้อมกลับแกน (อีก 3 แบบ) โดยเลือกแบบที่ผลรวมความคลาดเคลื่อนน้อยที่สุด
4. แสดงผลเป็นข้อความชัดเจน เช่น "ปกติ", "แกน X กลับด้าน", "แกน X/Y สลับกัน" พร้อมแผนภาพเป้าเทียบจุดที่แตะจริง และค่าความคลาดเคลื่อนเฉลี่ย (เป็นพิกเซลและเปอร์เซ็นต์)
5. หน้าที่สอง: ทดสอบลากเส้นจากมุมหนึ่งไปอีกมุม ให้ผู้ใช้เห็นว่าเส้นเดินตามนิ้วถูกทิศ

**เกณฑ์ตรวจรับ**

- ตัดสินได้ถูกต้องทั้ง 8 รูปแบบ (เขียน unit test ของฟังก์ชันตัดสินโดยจำลองพิกัด)
- ถ้าผู้ใช้แตะพลาดหรือสัญญาณไม่ชัดเจน (ความคลาดเคลื่อนสูงทุกรูปแบบ) ให้แสดง "ไม่แน่ใจ ลองใหม่" แทนการเดา
- มีปุ่มทำซ้ำ

**หมายเหตุ:** ฟังก์ชันนี้ครอบคลุมเฉพาะจอเดียว ส่วนปัญหา multi-monitor mapping (ทัชไปตรงกับจอผิดตัว) อยู่นอกขอบเขต

### Part 9: วัด Touch-to-Paint Latency

เป้าหมาย: วัดเวลาตั้งแต่ระบบส่ง input event จนถึงเฟรมที่แอปวาดผลลัพธ์เสร็จ

**วิธีวัด (ข้อเสนอ)**

- ใช้ `event.timeStamp` ของ Pointer Event เป็นจุดเริ่ม (เวลาที่ระบบรับ input)
- วาดผลบน canvas ภายใน `requestAnimationFrame` แล้ววัดเวลา ณ ตอนต้นเฟรมถัดไป (หรือหลังการ present) ด้วย `performance.now()` และคำนวณส่วนต่าง
- โหมดทดสอบ: ลากนิ้วเป็นวงกลมหรือแตะเป้าซ้ำ ๆ แล้วสุ่มตัวอย่างต่อเนื่อง

**สิ่งที่ต้องแสดง**

- ค่าเฉลี่ย, ต่ำสุด, สูงสุด, percentile 95 (ms) และกราฟสดของ 200 ตัวอย่างล่าสุด
- ค่าประเมินระดับ เช่น ดีมาก (< 20 ms), ดี (20-40), พอใช้ (40-80), ช้า (> 80) และแจ้งว่าตัวเลขเป็นเกณฑ์อ้างอิงคร่าว ๆ
- ข้อความกำกับ: "ค่านี้เป็นความหน่วงฝั่งซอฟต์แวร์ ไม่รวมเวลาตอบสนองของพาเนลจอ"
- ตรวจจับ frame drop (ช่วงที่ frame time เกิน 20 ms) แสดงจำนวน

**เกณฑ์ตรวจรับ**

- ไม่มี garbage หรือการจัดสรรหน่วยความจำมากในลูปวัด เพื่อไม่รบกวนผล
- ตัวเลขนิ่งพอเมื่อวัดซ้ำในเครื่องเดียวกัน (ส่วนเบี่ยงเบนไม่มากผิดปกติ)

## 6. รายการเสี่ยงที่ AI ต้องระวัง

- **WebKitGTK บน Linux:** รองรับ Pointer Events และ multi-touch ต่างกันตามเวอร์ชัน ต้องทดสอบจริงและเตรียม fallback
- **Linux ใช้ X11:** ผู้ใช้ยืนยันแล้ว ให้ทดสอบ fullscreen และ touch บน X11 เป็นหลัก ไม่ต้องรองรับ Wayland ในรอบแรก
- **สีเพี้ยนจาก WebView:** อย่าใช้ CSS filter, backdrop-filter หรือ opacity ทับพื้นที่ทดสอบ
- **Display scaling:** ห้ามสมมติว่า 1 CSS pixel = 1 พิกเซลจริง
- **ตัวเลข latency:** event.timeStamp บางแพลตฟอร์มอยู่คนละฐานเวลากับ `performance.now()` ต้องตรวจและปรับให้ตรงก่อนคำนวณ
