# แผนงานรอบที่ 2 — แก้ไขและเพิ่มฟีเจอร์ Display Tester

เอกสารนี้ต่อจาก `display-tester-plan.md` (แผนเดิม Part 1-10) และ `worklog.md` โดยแตกงานเป็น Part 11-16 ให้ AI คนละตัวทำทีละ Part ได้ แต่ละ Part อ่านและทำได้จบในตัว

## 0. กติกาสำหรับ AI ทุกตัว (อ่านก่อนเริ่ม)

1. ทำเฉพาะ Part ที่ได้รับมอบหมาย ห้ามแก้ไฟล์หรือฟีเจอร์นอกขอบเขตของ Part นั้น (ยกเว้นที่ระบุไว้ชัดเจน)
2. **ก่อนเขียนโค้ด** ให้อ่าน `worklog.md` และไฟล์โค้ดที่เกี่ยวข้องจริงก่อน เพราะเอกสารนี้เขียนจากบันทึก ไม่ได้เขียนจากโค้ดโดยตรง ชื่อไฟล์/ฟังก์ชันอาจต่างไปเล็กน้อย
3. หากข้อกำหนดไม่ชัดเจน ขัดกัน หรือกระทบสถาปัตยกรรม **ให้ถามผู้ใช้ก่อนเขียนโค้ด ห้ามเดา**
4. ทดสอบจริงทุก Part: รัน `npm run build` ให้ผ่าน, เขียน/รันชุดตรวจรับอัตโนมัติ (ตามแนว `scratch/verify-*.mjs` ที่มีอยู่) และแสดงผลลัพธ์ให้ผู้ใช้เห็น พร้อมขั้นตอนทดสอบด้วยมือบนจอทัชจริง
5. จบ Part แล้ว **หยุดรอผู้ใช้ยืนยัน** ก่อน push/merge หรือเริ่ม Part ถัดไป
6. จบ Part ให้เพิ่มหัวข้อใหม่ใน `worklog.md` (รูปแบบเดียวกับ Part เดิม: สถานะ / Branch / สิ่งที่ดำเนินการ / ผลการทดสอบ)
7. โค้ดต้องรันได้ทั้ง Linux (X11) และ Windows ห้ามเพิ่ม UI framework ยังคงใช้ Vanilla TS + Vite + Tailwind v3.4 และ UI ภาษาไทยอย่างเดียว
8. ข้อห้ามเดิมยังมีผล: พื้นที่ทดสอบห้ามมี filter / backdrop-blur / shadow / opacity / transition ทับ, ปุ่มสัมผัสไม่เล็กกว่า 64x64 px, ไม่บันทึกผลทดสอบลงไฟล์

## Part 11: คีย์บอร์ดไทยหรืออังกฤษใช้ได้ทุกหน้า

**ปัญหา:** ตอนนี้ปุ่มลัดเป็นตัวอักษร (H, D, R, C ฯลฯ) ถ้าคีย์บอร์ดตั้งเป็นภาษาไทยจะกดไม่ติดและต้องสลับภาษา

**แนวทาง**

- สร้างโมดูลกลาง เช่น `src/core/keys.ts` ฟังก์ชัน `normalizeKey(e: KeyboardEvent)` คืนชื่อปุ่มแบบตายตัวไม่ขึ้นกับภาษา โดยอ่านจาก `event.code` (ตำแหน่งปุ่มจริง เช่น `KeyH`, `KeyD`, `Digit1`) เป็นหลัก
- ปุ่มตัวเลขแถวบน `Digit1`-`Digit8` และ numpad ต้องใช้แทนกัน, `+`/`-` ให้รองรับ `Equal`/`Minus`/`NumpadAdd`/`NumpadSubtract`
- Fallback: ถ้า `event.code` ว่างหรือเป็น `Unidentified` (อาจเกิดบน WebKitGTK/X11 บางเครื่อง) ให้แปลงจากตัวอักษรไทยแบบ Kedmanee เป็นปุ่ม QWERTY ที่ตรงกัน โดยเก็บตารางแปลงไว้ในไฟล์เดียวกัน
- เปลี่ยนทุกจุดที่ใช้ `e.key` / `e.code` ตรง ๆ ให้เรียกผ่าน `normalizeKey` ทั้งหมด: `router.ts`, `hud.ts`, `fullscreen.ts`, `menu.ts` และโมดูลใน `src/tests/*` ทุกไฟล์ (ให้ `grep` หาทั้งโปรเจกต์ ไม่ดูเฉพาะรายชื่อนี้)
- ปุ่มที่ไม่ใช่ตัวอักษร (← → ↑ ↓ Esc F11 Space Home End Del Enter) ทำงานเหมือนเดิมและต้องไม่พัง
- ห้ามทำให้การพิมพ์/คีย์ลัดของระบบ (Ctrl, Alt, Meta + ปุ่มใด) ถูกจับผิด: ถ้ามี modifier ให้ปล่อยผ่าน ยกเว้นที่แอปใช้อยู่แล้ว
- ปรับข้อความ HUD/คำแนะนำให้ยังแสดงปุ่มเป็นตัวอักษรอังกฤษตามเดิม แต่เพิ่มหมายเหตุสั้น ๆ ใน README ว่ากดได้ทั้งคีย์บอร์ดไทยและอังกฤษ

**เกณฑ์ตรวจรับ**

- Unit test ของ `normalizeKey`: จำลอง event ที่มี `code` ตรงกับปุ่มทุกตัวที่แอปใช้ แต่ `key` เป็นตัวอักษรไทย (เช่น `code='KeyH', key='้'`) ต้องได้ผลเหมือนคีย์อังกฤษ และทดสอบ fallback เมื่อ `code` ว่าง
- ไม่มีโค้ดค้างที่อ่าน `e.key` เป็นตัวอักษรตรง ๆ เพื่อตัดสินคีย์ลัด (แสดงผล `grep` เป็นหลักฐาน)
- ทดสอบมือ: ตั้งคีย์บอร์ดเป็นไทย กดคีย์ลัดครบทุกหน้า (เมนู 1-8, H, D, R, C, Space, +/-, ลูกศร ฯลฯ) ทำงานเหมือนตอนเป็นอังกฤษ

## Part 12: เมนูหลัก — เอาการ์ดข้อมูลระบบออก

**ปัญหา:** เมนูมีข้อมูลระบบ 2 ที่ ที่หนึ่งเป็นการ์ดข้อมูลจอภาพ (Info) อยู่ใกล้ปุ่ม 7 หัวข้อ อีกที่อยู่มุมขวาบน

**งาน**

- ลบการ์ดข้อมูลจอภาพที่อยู่ใกล้ปุ่มหัวข้อทดสอบออกจาก `menu.ts` **เก็บเฉพาะอันมุมขวาบน** (ปุ่ม/ไอคอนที่เปิด `info-modal.ts`) ไว้
- ปรับ layout ปุ่มหัวข้อให้ใช้พื้นที่ที่ว่างเพิ่มขึ้นอย่างเหมาะสม ยังต้อง responsive และไม่ล้นที่ 1024x768, 1280x720, 1920x1080 (เมนูอาจมี 8 ปุ่มหลัง Part 16 ให้เผื่อ layout ไว้: เช่น กริด 4x2 หรือ 2x4 ตามขนาดจอ)
- ลบโค้ดที่ไม่ถูกใช้แล้ว (ฟังก์ชัน/สไตล์ของการ์ดที่เอาออก) ให้สะอาด แต่ **ห้ามลบ** `info-modal.ts` และ `display-info.ts` เพราะยังใช้อยู่

**หากไม่แน่ใจว่า "อันมุมขวาบน" คืออะไรในโค้ดจริง ให้ถามผู้ใช้พร้อมแนบ screenshot หรือคำอธิบายสิ่งที่พบ**

**เกณฑ์ตรวจรับ**

- เมนูมีข้อมูลระบบเหลือแค่ปุ่มมุมขวาบนที่เดียว กดแล้วเปิดหน้าข้อมูลได้เหมือนเดิม
- ไม่ล้น/ไม่ตกขอบที่ 3 ขนาดจอข้างต้น (แสดง screenshot หรือผลการวัดขนาด)
- เมาส์ ทัช และคีย์ลัดเลขยังเข้าหัวข้อได้เหมือนเดิม

## Part 13: แก้ทดสอบสี (เมนู 3) — กด D แล้วค่า RGB ไม่ตรง

**อาการ (ผู้ใช้ยืนยันแล้ว):** ตอนกด `D` เพื่อตรวจค่าสี ค่า RGB ที่แสดงมีแค่ `255,255,255` หรือ `0,0,0` เท่านั้น ไม่ตรงกับสีที่ชี้อยู่ **ต้องแก้ให้แสดงค่าสีของพิกเซลที่ตำแหน่งที่ชี้จริง** (เช่น ชี้แท่งสีแดงต้องได้ 255,0,0 ชี้เทา 50% ต้องได้ค่าเทานั้น ชี้ gradient ต้องได้ค่าที่เปลี่ยนตามตำแหน่ง)

ข้อสังเกต: การได้แต่ 0 หรือ 255 สื่อว่าน่าจะอ่านผิดตำแหน่ง/ผิดเลเยอร์ (เช่น อ่านโดนพื้นดำ/ขอบขาว/กรอบของ picker/overlay) หรืออ่านจากพิกัดที่อยู่นอกพื้นที่ภาพ ไม่ใช่ปัญหา color profile

**ขั้นตอน (ต้องทำตามลำดับ)**

1. **หาสาเหตุจริงก่อน** อย่าเดา: เขียนสคริปต์/โค้ดทดสอบที่ไล่ทุกภาพทดสอบ (ทั้ง 12 รูปแบบย่อย) แล้วเทียบ "ค่าที่นิยามไว้" กับ "ค่าที่ `getImageData` อ่านได้" ที่ตำแหน่งตัวอย่างหลายจุด รายงานผลเป็นตารางให้ผู้ใช้เห็น
2. ตรวจสมมติฐานเหล่านี้ (เรียงตามความน่าจะเป็น ให้เริ่มจากสองข้อแรกเพราะตรงกับอาการ 0/255):
   - พิกัดที่อ่านเป็น CSS pixel แต่ canvas เป็นพิกเซลจริง (ไม่คูณ `devicePixelRatio`) ทำให้อ่านผิดตำแหน่ง โดยเฉพาะ gradient / color bars ที่ค่าเปลี่ยนตามตำแหน่ง
   - อ่านค่าหลังจากวาด overlay (crosshair, ป้ายค่า, HUD, กรอบ picker) ลงบน canvas เดียวกัน ทำให้อ่านโดนสีของ overlay
   - แอปแสดงค่าที่ "คำนวณจากสูตร" ไม่ใช่ค่าที่อ่านจริง หรือ rounding ต่างกัน (เช่น gradient ไม่ปัดเศษเหมือนกัน)
   - ตำแหน่งอ้างอิงเป็นตำแหน่งเมาส์ล่าสุด/จุดกึ่งกลางโดยไม่ตั้งใจ ไม่ใช่จุดที่ผู้ใช้เล็ง
   - `colorSpace` ของ canvas/context ไม่ได้ตั้งเป็น `srgb` ชัดเจน, มีการ smoothing/dithering หรือ `globalAlpha` ค้าง
   - canvas ถูก scale ด้วย CSS ทำให้ตำแหน่งเมาส์ไม่ตรงกับพิกเซล canvas
3. แก้ที่ต้นเหตุ แล้วทดสอบซ้ำ ถ้าค่าที่อ่านจาก canvas ตรงตามนิยามแล้วแต่ผู้ใช้ยังเห็นว่า "ไม่ตรง" ให้อธิบายผู้ใช้ว่าตัวเลขนี้คือค่าใน buffer ของ canvas ไม่ใช่ค่าที่ออกจอจริง (แอปอ่านผลหลัง color profile ของระบบไม่ได้) และปรับข้อความในหน้า inspector ให้ระบุข้อนี้
4. ถ้าหาอาการไม่เจอหรือยังเกิดอยู่ ให้ถามผู้ใช้ว่าเกิดกับภาพทดสอบไหน, ชี้ด้วยเมาส์หรือทัช, ค่าที่ควรได้กับค่าที่เห็นคืออะไร (ขอตัวอย่าง 2-3 กรณี)

**เกณฑ์ตรวจรับ**

- ตารางเทียบ "ค่านิยาม vs ค่าที่ picker แสดง" ครบทุกภาพทดสอบ ตรงกัน 100% (สีเต็มจอ 8 สีต้องตรงเป๊ะ เช่น แดง = 255,0,0)
- Picker ต้องคืนค่า **ที่ไม่ใช่แค่ 0/255** เมื่อชี้ gradient, เทา 25/50/75% และช่องสีผิว/ท้องฟ้า/หญ้า (แสดงตัวอย่างค่าที่อ่านได้)
- ผลต้องตรงที่ `devicePixelRatio` = 1, 1.25 และ 1.5 (จำลองด้วย mock ก็ได้ถ้าเปลี่ยน scale จริงไม่สะดวก)
- Picker ไม่วาด overlay ลงบน canvas เดียวกับภาพทดสอบ (ใช้ layer แยก หรืออ่านค่าก่อนวาด overlay) และไม่ทำให้ภาพทดสอบเปลี่ยน
- ยังใช้ปุ่ม D ได้ทั้งคีย์บอร์ดไทย/อังกฤษ (ผ่าน Part 11)

## Part 14: แก้แสงรั่ว/Mura (เมนู 5) — โหมดตารางใช้ 5x5 อย่างเดียว

**งาน**

- โหมดตารางโซน (ที่เดิมมี 3x3 และ 5x5) ให้เหลือ **5x5 อย่างเดียว** ลบ 3x3 ออก ทั้งจากรายการพรีเซ็ต, การวนด้วยปุ่ม, ข้อความ HUD และ README

- ตรวจว่าการปรับระดับเทาละเอียดทีละ 1/255, สไลเดอร์ และการซ่อน UI อัตโนมัติยังทำงานในโหมด 5x5

**เกณฑ์ตรวจรับ**

- ในหน้า Light Bleed ไม่มีโหมด 3x3 เหลืออยู่ (ตรวจ `grep` ว่าไม่มีคำว่า 3x3 / 3×3 / 9 โซน ในโค้ดและเอกสารของหน้านี้)
- โหมด 5x5 แสดง 25 บล็อกเทาเท่ากันเต็มจอ ไม่มีช่องว่างที่ขอบ
- เลื่อนพรีเซ็ตวนครบรอบโดยไม่ข้ามหรือซ้ำ

## Part 15: แก้เช็คทิศทาง Touch (เมนู 6)

### 15.1 หน้า 6.2 (ลากเส้น) มีเส้นโผล่ต่อกันเอง

**อาการ:** แตะมุมซ้ายบน 1 ครั้ง แล้วแตะมุมขวาล่าง 1 ครั้ง อยู่ดี ๆ มีเส้นลากเชื่อมสองจุดนั้น ทั้งที่ไม่ได้ลาก

**แนวทางแก้ (ตรวจที่ `touch-axis.ts` ว่าเป็นสาเหตุใด)**

- สาเหตุที่น่าจะเป็น: เก็บจุดของเส้นไว้ใน array เดียวแล้ววาดเชื่อมจุดสุดท้ายของ stroke เก่ากับจุดแรกของ stroke ใหม่ หรือวาดตามทุก `pointermove` โดยไม่เช็คว่ากำลังกดอยู่
- แก้ให้ 1 `pointerdown` = เริ่ม stroke ใหม่ (วาดเป็นจุดเดี่ยวก่อน), `pointermove` วาดต่อเฉพาะ pointer ที่กดอยู่ (เก็บแยกตาม `pointerId`), `pointerup` / `pointercancel` / `pointerleave` ปิด stroke
- เมาส์ที่เลื่อนเฉย ๆ โดยไม่กดห้ามวาด

### 15.2 จาก 6.1 ไป 6.2 ปุ่มไม่ถูกตั้งค่าใหม่

**อาการ:** พอเปลี่ยนจากหน้าแตะ 4 มุม (6.1) ไปหน้าลากเส้น (6.2) ปุ่ม/ตัวควบคุมยังเป็นชุดของ 6.1

**งาน**

- ทำให้แต่ละหน้า (stage) มีชุดปุ่มและข้อความ HUD ของตัวเอง และ re-render ทุกครั้งที่เปลี่ยน stage พร้อมล้าง state ของ stage เดิมที่ไม่ควรค้าง
- **ข้อเสนอชุดปุ่ม (ค่าตั้งต้น ถ้าผู้ใช้ไม่ได้ระบุอย่างอื่น):**
  - 6.1: ปุ่ม "ทดสอบใหม่" (หรือ `R`) และ "ไปหน้าลากเส้น" (หรือ `→`)
  - 6.2: ปุ่ม "ล้างเส้น" (หรือ `R`) และ "กลับไปแตะ 4 มุม" (หรือ `←`)
- ปุ่มทุกปุ่มสูง/กว้างไม่ต่ำกว่า 64 px และกดได้ด้วยทัช
- **ถ้า AI พบว่าปุ่มที่ผู้ใช้หมายถึงต่างจากนี้ ให้ถามผู้ใช้ก่อนแก้**

**เกณฑ์ตรวจรับ**

- ทดสอบอัตโนมัติ: จำลอง pointer event "แตะซ้ายบน → แตะขวาล่าง" ต้องไม่มี segment เส้นเชื่อมสองจุดนั้น, จำลองการลากต่อเนื่องต้องมีเส้นต่อเนื่องถูกต้อง, จำลองหลายนิ้วต้องไม่มีเส้นข้ามนิ้ว
- ทดสอบอัตโนมัติ: สลับ stage ไปมา 20 รอบ ชุดปุ่มและ HUD ตรงกับ stage ปัจจุบันทุกครั้ง และ state เก่าไม่ค้าง
- Unit test เดิมของการตัดสิน 8 รูปแบบแกน ยังผ่านครบ (ห้ามแก้ตรรกะตัดสินเว้นแต่จำเป็น)
- ทดสอบมือบนจอทัชจริง: ตามอาการข้อ 15.1 และสลับ 6.1 ↔ 6.2 ไม่มีปุ่มค้าง

## Part 16: เพิ่มการทดสอบด้วยวิดีโอ + โฟลเดอร์วิดีโอ (เมนู 8)

**เป้าหมาย:** เล่นวิดีโอเต็มจอเพื่อดูภาพเคลื่อนไหวบนจอที่ทดสอบ (เช่น ความลื่นไหล การฉีกของภาพ สี) โดยผู้ใช้ใส่ไฟล์วิดีโอของตัวเองลงในโฟลเดอร์ที่กำหนด

### 16.1 โฟลเดอร์วิดีโอ

- ชื่อโฟลเดอร์ `videos`
- **ค่าตั้งต้น:** อยู่ข้างไฟล์ที่รันแอป (โหมด dev ใช้ `videos/` ที่รากโปรเจกต์) สร้างให้อัตโนมัติถ้ายังไม่มี
- ข้อควรระวัง: ถ้าติดตั้งแบบ MSI/NSIS ลง `Program Files` โฟลเดอร์ข้างตัวโปรแกรมอาจเขียนไม่ได้ ให้ตรวจสิทธิ์ ถ้าเขียนไม่ได้ให้ fallback ไปโฟลเดอร์ `videos` ใน app local data dir ของ Tauri และแสดงพาธจริงที่ใช้ในหน้าจอ
- Rust command เล็ก ๆ สำหรับ (1) หา/สร้างโฟลเดอร์ (2) คืนรายการไฟล์ (ชื่อ, พาธ, ขนาด) เรียงตามชื่อ นามสกุลที่รับ: `.mp4 .webm .mkv .mov .m4v .ogv` (ให้ browser engine เป็นตัวตัดสินว่าเล่นได้หรือไม่)
- เพิ่มปุ่ม "เปิดโฟลเดอร์วิดีโอ" ถ้าทำได้ง่ายด้วย plugin ของ Tauri (ไม่บังคับ ถ้าเพิ่มภาระมากให้แสดงพาธให้ผู้ใช้เปิดเองแทน)
- เพิ่ม `videos/.gitkeep` และใส่ `videos/*` ใน `.gitignore` (ยกเว้น `.gitkeep`) **ห้าม commit ไฟล์วิดีโอ และห้ามฝังวิดีโอลงใน installer**

### 16.2 การเล่นไฟล์

- ใช้ `<video>` element จริงเล่นไฟล์ในโฟลเดอร์ผ่าน asset protocol (`convertFileSrc`) ตั้ง `assetProtocol` และ scope ให้เฉพาะโฟลเดอร์วิดีโอ (ห้ามเปิด scope กว้างทั้งเครื่อง) ตรวจให้แน่ใจว่า seek ได้ (Range request)
- ถ้าเปิด/เล่นไฟล์ไม่ได้ (codec ไม่รองรับ) ต้องแสดงข้อความภาษาไทยชัดเจนว่าเล่นไฟล์นี้ไม่ได้และข้ามไปไฟล์ถัดไปได้ ห้ามค้างหน้าดำ ข้อควรรู้: บน Linux (WebKitGTK) codec ขึ้นกับ GStreamer plugin ที่ติดตั้ง (เช่น H.264 อาจต้องลง `gstreamer1.0-libav`) ให้เขียนใน README และข้อความ error
- ก่อนเขียนโค้ดหลัก ให้ทดสอบเร็ว ๆ ว่า `.mp4` (H.264) และ `.webm` เล่นได้บน Windows และ Linux ของผู้ใช้ ถ้าเล่นไม่ได้ในสภาพแวดล้อมใดให้รายงานผู้ใช้ก่อนทำต่อ

### 16.3 หน้าจอและการควบคุม

- หน้ารายการ: แสดงชื่อไฟล์เป็นปุ่มใหญ่ (สูง ≥ 64 px) เลื่อนดูได้ และแสดงพาธโฟลเดอร์ ถ้าว่างให้แสดงข้อความ "ยังไม่มีวิดีโอ ใส่ไฟล์ในโฟลเดอร์: <พาธ>" และปุ่มสแกนใหม่ (`R`)
- หน้าเล่น: พื้นหลังดำ วิดีโอเต็มจอ **ไม่มี UI ใด ๆ ทับวิดีโอ** (HUD ซ่อน/แสดงด้วย `H` ตามมาตรฐานเดิม)
- โหมดแสดงผล (สลับด้วย `Z`): พอดีจอ (รักษาสัดส่วน) / ขนาดจริง 1:1 (ไม่ scale) / ยืดเต็มจอ
- ปุ่มลัด: `Space` เล่น/หยุด, `←`/`→` ไฟล์ก่อนหน้า/ถัดไป, `L` วนซ้ำ (ค่าตั้งต้น: เปิด), `M` ปิด/เปิดเสียง, `Esc` กลับรายการ/เมนู
- ทัช/เมาส์ (หน้าเล่นไม่ใช้ทัชทดสอบจึงใช้ได้): แตะ 1/3 ซ้ายจอ = ก่อนหน้า, 1/3 ขวา = ถัดไป, ตรงกลาง = เล่น/หยุด การกดค้างมุมซ้ายบนยังกลับเมนูตามเดิม
- HUD แสดง: ชื่อไฟล์, ความละเอียดวิดีโอ, เวลา, โหมดแสดงผล, จำนวนเฟรมที่ตกจาก `getVideoPlaybackQuality()` (ถ้ามี)
- ทำเป็นโมดูลใหม่ `src/tests/video.ts` ตามอินเทอร์เฟซ `TestModule` เดิม และเชื่อมใน `tests/index.ts`, router, เมนู (ปุ่มที่ 8, คีย์ลัด `8`), ปรับข้อความ "7 หัวข้อ" ทั้งหมดในโค้ดและ README เป็น 8
- `stop()` ต้องหยุดวิดีโอ ปล่อย `src` ของ `<video>` และล้าง listener/RAF ครบ (ไม่ memory leak เมื่อเข้า-ออก 50 รอบ ตามเกณฑ์เดิม)
- ไม่ใส่ filter/shadow/opacity/transition ทับ element วิดีโอ

### 16.4 เกณฑ์ตรวจรับ

- ใส่ไฟล์ `.mp4` และ `.webm` ในโฟลเดอร์ → ปรากฏในรายการและเล่นเต็มจอได้บนทั้ง Windows และ Linux (หรือรายงานชัดเจนว่าไฟล์/codec ใดเล่นไม่ได้บนระบบใด)
- โฟลเดอร์ว่าง/ไม่มีโฟลเดอร์ → สร้างให้เอง และแสดงข้อความแนะนำ ไม่ error
- ไฟล์เสีย หรือ codec ไม่รองรับ → แสดงข้อความภาษาไทยและข้ามได้ ไม่ค้าง
- ทดสอบเข้า-ออกหน้านี้ 50 รอบ ไม่มี listener/RAF/วิดีโอค้าง
- ทดสอบที่ 1024x768 และ 1920x1080 ทุกโหมดแสดงผล (พอดีจอ / 1:1 / ยืด) ถูกต้อง
- `.gitignore` ไม่ให้ไฟล์วิดีโอหลุดเข้า Git
